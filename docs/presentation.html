⚠️ Problem Statement: Gate No. 2 Operational Chaos

The operational gap between courier truck drop-offs and verified student collection

Slide 02 / 16 • 1:00

The Gate No. 2 Bottleneck

  • 400+ Daily Shipments: Arriving erratically from Amazon, Flipkart, BlueDart, DTDC, and India Post.
  • Manual Paper Registers: Prone to illegible handwriting, lost pages, and zero instant queryability.
  • Identity Impersonation: Lack of cryptographic authentication allows unauthorized collections.
  • Storage Shelf Overflow: Random placement leads to damaged packages and long search queues.
  • Overdue Parcel Stagnation: No automated alerts when packages remain uncollected for days.

CDMS Digital Transformation

  • Immutable Custody Chain: Every status transition digitally signed and logged.
  • Single-Use Cryptographic Tokens: 6-digit salted HMAC codes with 30-min TTL.
  • Automated 3-Day Overdue Audit: Automated daily student notifications and metric increments.

🏗️ End-to-End System Architecture (Layered Monolith)

Clean / Onion Architecture with strict boundary enforcement

Slide 03 / 16 • 1:15

Clean Layered Separation

  • 1. Presentation Layer: React 18, Vite, Tailwind CSS, Lucide icons, Bilingual i18n context.
  • 2. API & Presenter Layer: FastAPI REST routes, OAuth2 JWT bearer auth, Pydantic v2 DTOs, Role-Aware Presenters.
  • 3. Application Services: PackageIntakeService, StorageAllocationService, PickupService, PackageTransitioner.
  • 4. Pure Domain Core: Finite State Machine, Strategy algorithms, Pickup token rules, In-process EventBus (0 framework dependencies).
  • 5. Persistence Layer: Unit of Work, PyMongo repositories with atomic CAS queries.

Architectural Justification: Why Not Microservices?

  • Avoids distributed transaction overhead (no 2-phase commit or complex Sagas needed).
  • Provides sub-15ms p95 latency on single server instances.
  • Maintains strict domain boundaries ready for future microservice extraction if campus scales to 50+ gates.

Role-Based Access Control & Functional Boundaries

Three Enforced Human Actors

  • Security Staff (SECURITY_STAFF): Ingest shipments, verify recipient identity, allocate shelves, verify pickup tokens, execute physical handover.
  • Learners (LEARNER): Track packages, receive arrival alerts, generate single-use 6-digit pickup tokens, report package issues.
  • Operations Admins (OPERATIONS_ADMIN): Supervise facility bin utilization, resolve damaged/unidentified parcels, review audit logs.

Functional & Non-Functional Matrix

  • FR-1 to FR-6: Rapid barcode intake, size-aware bin allocation, multi-channel notifications, cryptographic tokens, atomic handover, dispute management.
  • NFR-1 (Atomicity): Zero double-delivery, zero shelf overfills under concurrency.
  • NFR-2 (Security): Data isolation (learners only see their own packages); salted HMAC tokens.
  • NFR-3 (Idempotency): Safe retries on all mutations via Idempotency-Key.

Abstraction, Encapsulation, Inheritance, and Polymorphism in Python

  • StorageAllocationStrategy protocol declares only rank().
  • NotificationChannel protocol declares only send().

2. Encapsulation

  • StorageCandidate.accepts(size) encapsulates shelf dimension ranking and capacity limits. External callers cannot bypass these rules.

3. Inheritance & 4. Polymorphism

💎 Criterion 4: SOLID Principles Mapped to Code

Clean architectural proof for each of the 5 SOLID design tenets

Slide 07 / 16 • 1:30

The 5 Principles in CDMS

  • S (Single Responsibility): Dedicated services: PackageIntakeService (intake), StorageAllocationService (shelving), PickupService (token/handover), AuditService (audit).
  • O (Open/Closed): New allocation strategies or notification channels are added via registration in container.py without editing existing service logic.
  • L (Liskov Substitution): SuitableSizeStrategy and FirstAvailableStrategy are fully interchangeable; both honor the same contract without side effects.
  • I (Interface Segregation): Micro-protocols (StorageAllocationStrategy has only 1 method: rank; NotificationChannel has only send).
  • D (Dependency Inversion): High-level services receive abstract protocols via constructors; choices wired in Composition Root (container.py).
# services/storage_allocation.py - Dependency Inversion in action class StorageAllocationService: def __init__(self, uow: UnitOfWork, strategy: StorageAllocationStrategy) -> None: self._uow = uow self._strategy = strategy # Depends on abstraction, not concrete class!

🔄 Criterion 6: Sequence & Activity Diagrams (Key Use Cases)

Intake, Token Issuance, and Concurrency-Safe Handover

Slide 09 / 16 • 1:30

Handover Sequence Message Flow

  • 1. Identification: Student gives ID and 6-digit code to Guard at Gate No. 2.
  • 2. Verification: PickupService verifies recipient, expiry, and matches HMAC-SHA256 salt hash.
  • 3. Atomic Token CAS: mark_used() executes find_one_and_update on used_at: None. Exactly 1 concurrent request can win!
  • 4. State Machine Transition: Moves to COLLECTED; releases shelf slot.
  • 5. Handover Proof: Writes immutable PickupRecord (UNIQUE(package_id)).

Activity Alternate Flows

  • Expired Token (>30 min) → Rejection with PICKUP_CODE_EXPIRED.
  • 3 Failed Attempts → Token permanently locked (PICKUP_CODE_LOCKED).
  • Damaged on arrival → Diverts to DAMAGED holding state & opens incident.

🗄️ Criterion 8: Database Schema, Indexing & Concurrency Control

10 Collections, Compound Indexes, and Atomic CAS Operations

Slide 11 / 16 • 1:15

Database-Level Unique Constraints

  • users.institutional_id & users.email (Unique).
  • packages.tracking_id & packages.internal_code (Unique).
  • pickup_records.package_id (Unique → Physically guarantees zero double collections).
  • idempotency_keys(user_id, scope, key) (Unique).

Atomic Compare-And-Swap (CAS) in Action

  • Shelf Reservation: find_one_and_update({"_id": id, "is_active": True, "$expr": {"$lt": ["$occupied_count", "$capacity"]}}, {"$inc": {"occupied_count": 1}})
  • Token Redemption: find_one_and_update({"_id": id, "used_at": None, "revoked_at": None}, {"$set": {"used_at": now}})
  • Outcome: Guaranteed race-free execution without distributed locks.

🛡️ Criterion 9: Error Handling, Validation & 20 Edge Cases

Defensive Programming, Brute-Force Lockout, and Automated Overdue Tracking

Slide 12 / 16 • 1:15

Real-World Edge Cases Defended

  • Double Handover Race: Blocked by atomic token CAS & unique pickup_records index.
  • Shelf Overbooking: Atomic occupied_count < capacity check prevents overfills.
  • Brute Force Code Guessing: 3 failed attempts lock token; IP sliding window rate limit.
  • Salted HMAC Hash: Zero plaintext tokens in database; immune to database leak.
  • Token Expiry: Strict 30-minute validity enforced.
  • Damaged on Arrival: Held in DAMAGED state; incident ticket opened.
  • Unidentified Recipient: Stored in holding queue until claimed with tracking ID.
  • Automated 3-Day Overdue: Daily notifications sent; awaiting_storage stat incremented.
